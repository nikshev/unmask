# Research: Публічний API і Telegram-бот доставки аналізу (004)

Дата: 2026-10-05. Усі рішення — під стек проєкту (Python 3.12, `pytest`, залежності
`pyyaml`/`solders`/`httpx`; dev `pytest`/`jsonschema`) і під ядро 001→002→003, що не змінюється.

## R-1. HTTP-шар: stdlib `http.server`, без нового фреймворку

- Decision: один процес, `http.server.ThreadingHTTPServer` + маленький роутер на один маршрут
  `GET /api/token/{mint}` (плюс `GET /healthz` для оператора).
- Rationale: ендпоінт один, повертає JSON; масштаб — демо і журі, не прод-навантаження.
  Нуль нових залежностей; обробка запиту — тонка обгортка над чистими функціями пакета доставки,
  тож тести ганяють логіку без сокетів (гард мережі `tests/conftest.py` лишається чинним).
- Alternatives considered: FastAPI/aiohttp — відкинуто: асинхронність і валідація схем з коробки
  не потрібні (схема відповіді перевіряється `jsonschema` у тестах, як схеми 001/002/003);
  кожна нова залежність — поверхня для ревʼю перед дедлайном без вигоди для MVP.

## R-2. Telegram: сирі виклики Bot API через `httpx`, long polling

- Decision: бот — цикл `getUpdates` (long polling) + прямі виклики `sendMessage`/`sendPhoto`/
  `answerCallbackQuery`/`editMessageText` через наявний `httpx`. Окремої бібліотеки для Telegram немає.
- Rationale: боту потрібні пʼять методів API з плоскими JSON-тілами; обгортка важча за сам протокол.
  Токен бота — лише з оточення (`UNMASK_BOT_TOKEN`), за зразком `HttpRpcSource.from_env()` (FR-004-10).
  Транспорт інжектований інтерфейсом (`BotTransport`: `send_message`/`send_photo`/`answer_callback`),
  тож тести підміняють несправжній транспорт із записаними відповідями ядра (FR-004-09).
- Alternatives considered: `python-telegram-bot` — відкинуто з тієї самої причини, що R-1.

## R-3. PNG: Pillow — єдина нова залежність фічі

- Decision: растровий рендер через Pillow (`PIL.Image`, `ImageDraw`, вбудований бітмап-шрифт).
  Стандартної бібліотеки для PNG у Python немає, а PRD вимагає саме PNG у повідомленні.
- Rationale: Pillow — найменша цільова залежність (без наукового стеку); малює прямокутники/кола/текст,
  чого достатньо для статичної схеми кластерів. Константи розкладки (розміри, кольори, обрізання
  адрес) — суто показові: на кластери/впевненість/`risk_score`/смугу не впливають (FR-004-11),
  документуються в `data-model.md`, версіонування їм не потрібне.
- Alternatives considered: matplotlib — відкинуто (важкий, тягне numpy; інтерактивність PRD
  прямо заборонена); SVG засобами stdlib — відкинуто (Bot API `sendPhoto` не приймає SVG);
  зовнішній рендер-сервіс — відкинуто (мережева залежність у критичному шляху демо).
- Наслідок для конституції: виняток із «без нових залежностей» 001–003 — обґрунтований тут,
  бо PNG інакше неможливий; залежність не впливає на висновки аналізу (принцип III чистий).

## R-4. Живий конвеєр: ті самі сервіси 001→002→003, секрети з оточення

- Decision: запит жене `IngestService.collect(mint)` → `GraphService.analyze` → `ClusterService.analyze`
  з завантаженими з `config/*.yaml` конфігами; RPC-джерело — `HttpRpcSource.from_env()`.
  `Rejection` (невалідний mint, токен не знайдено) мапиться у відповідь-помилку, не у виняток.
- Rationale: FR-004-02 забороняє окремі «демо-пороги»; пере використання готових сервісів дає це
  безкоштовно разом з їхніми кешами (`ResultCache` 001) і чесною неповнотою.
- Alternatives considered: окремий спрощений збір для демо — відкинуто (роздвоєння джерела істини
  перед суддями з Data & Analytics).

## R-5. Кеш доставки: памʼять процесу + single-flight

- Decision: `mint → документ відповіді` у памʼяті процесу; одночасні запити одного нового токена
  чекають один збір (single-flight на події/блоківці); політика інвалідації — жодної на вікно демо
  (перезапуск чистить кеш; задокументовано). Неповні документи кешуються з позначкою неповноти.
- Rationale: PRD вимагає миттєвий повтор і ≤ 60 с холодного; два запити не мають подвоювати RPC.
  Персистентність не потрібна до демо (принцип VII: без власного сховища).
- Alternatives considered: дисковий кеш/TTL — відкинуто для MVP (стан на диску = інвалідація,
  міграції, ще один контракт; додається після хакатону за потреби).

## R-6. Тестова стратегія без мережі і сокетів

- Decision: три рівні дублів — (1) записаний `RpcSource` (віддає зафіксовані `IngestResult`-словники
  з `tests/fixtures/real/`), (2) несправжній `BotTransport` (пише виклики в журнал), (3) HTTP-рівень
  тестується викликом функцій обробника напряму, без сокетів (гард `conftest.py` забороняє `connect`).
  Наскрізний тест: записаний транспорт → документ → валідація проти схеми відповіді.
- Rationale: принцип II; сокети в тестах заборонені наявним гардом, тож архітектура мусить
  відділяти чисту логіку від транспорту з самого початку (див. `data-model.md`, «Звʼязки»).

## R-7. Контракт відповіді: JSON Schema + походження висновку

- Decision: `contracts/api-response.schema.json` — надмножина PRD-таблиці: поля PRD плюс блок
  `provenance` (версії конфігів 001/002/003, `analyzed_at`, повнота з причинами) і явний знаменник
  `supply_share` (частка серед проаналізованих покупців — assumption 003; PRD називає поле
  `supply_share`, контракт документує, що саме воно означає).
- Rationale: принцип V — число без походження не повертається; сторонній сервіс бачить версії,
  на яких зроблено висновок, і не порівнює прогони різних версій (принцип III).

## R-8. Довгі докази і порожній граф

- Decision: текст кнопки «докази» стискається до ліміту повідомлення (~4000 символів): перші N
  доказів повністю + рядок «і ще K»; повний перелік — другим повідомленням/файлом за тим самим
  callback. Порожній граф → PNG-заглушка з підписом «кластерів не знайдено».
- Rationale: ліміти Bot API — властивість платформи, а не наш вибір; обрізання без втрати доступу
  до повного тексту зберігає принцип V.
