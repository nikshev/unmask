# Feature Specification: Публічний API і Telegram-бот доставки аналізу

**Feature Branch**: `004-api-bot-delivery` (робота ведеться в `main`, окрема гілка не створюється)

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "За PRD MVP: публічний HTTP-ендпоінт GET /api/token/{mint} (кластери з доказами й оцінка ризику), Telegram-бот без веб-сторінки — команда /check <mint> одним повідомленням повертає оцінку ризику, частки найбільших кластерів, PNG-картинку графа й кнопку «докази», серверний PNG-рендер без інтерактивності, кеш результату за адресою токена, холодна відповідь до 60 секунд, неіснуючий mint без падіння, жодної авторизації. Ядро 001→002→003 готове і не змінюється."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Перевірка токена через API (Priority: P1)

Сторонній сервіс (інтегратор, журі треку Panta API) викликає `GET /api/token/{mint}` і отримує JSON: адресу токена, час аналізу, розмір вибірки, кластери, відсортовані за часткою (у кожному — гаманці, частка, впевненість, перелік доказів із джерелом і вікном), загальну оцінку ризику 0–100 і смугу. Кожне число супроводжується доказами й походженням (версії конфігів, статус повноти).

**Why this priority**: це єдиний машинний інтерфейс продукту; без нього треки Panta API й аналітичні інтеграції неможливі. PRD називає публічний ендпоінт однією з трьох цілей MVP.

**Independent Test**: запит із зафіксованим записом транспорту (без мережі) для збереженого результату збору повертає документ із усіма полями PRD-таблиці; кожен кластер має непорожній `evidence[]`; повторний запит повертає той самий документ.

**Acceptance Scenarios**:

1. **Given** токен зі збереженим збором, де кластеризація знаходить кластер, **When** викликано ендпоінт, **Then** відповідь містить `mint`, `analyzed_at`, `wallets_analyzed`, `clusters[]` за часткою спадно, у кожному `wallets`, `supply_share`, `confidence`, `evidence[]` (тип, джерело, вікно), і `risk_score` 0–100.
2. **Given** токен без кластерів на повних даних, **When** викликано ендпоінт, **Then** `clusters` порожній, смуга «чисто» з явним поясненням, а не просто нуль.
3. **Given** неповний аналіз (обірваний збір, таймаут RPC), **When** викликано ендпоінт, **Then** відповідь несе статус неповноти з причинами й ніколи не показує «чисто».
4. **Given** невалідний `mint`, **When** викликано ендпоінт, **Then** помилка 4xx з людським поясненням, без стеку й без падіння процесу.

### User Story 2 - Перевірка токена через Telegram-бота (Priority: P1)

Трейдер надсилає боту `/check <mint>` і одним повідомленням отримує: оцінку ризику зі смугою, частки найбільших кластерів, картинку графа й кнопку «докази», яка розгортає, на чому побудований висновок (перелік доказів по кластерах). Веб-сторінки немає.

**Why this priority**: це демо-інтерфейс PRD («живий продукт: вводимо mint, бачимо граф і кластери») і те, що показують у перші 100 секунд демо-відео. Без бота немає демо.

**Independent Test**: драйвер бота без мережі (записані відповіді ядра + несправжній транспорт Telegram) на збереженому токені: команда `/check` дає одне повідомлення з оцінкою, частками, прикріпленим PNG і кнопкою; натискання кнопки показує докази.

**Acceptance Scenarios**:

1. **Given** токен із кластером високої концентрації, **When** надіслано `/check <mint>`, **Then** повідомлення містить смугу й число ризику, частки топ-кластерів, PNG-картинку й кнопку «докази».
2. **Given** натиснуто кнопку «докази», **When** бот обробляє callback, **Then** користувач бачить перелік доказів по кластерах (тип, джерело, вікно), на яких побудовано число.
3. **Given** токен без кластерів, **When** надіслано `/check <mint>`, **Then** повідомлення прямо каже, що пов'язаних груп не знайдено, з застереженням про повноту даних.
4. **Given** невалідний `mint`, **When** надіслано `/check <mint>`, **Then** бот відповідає зрозумілою помилкою й лишається живим.

### User Story 3 - Картинка графа для демо (Priority: P2)

До повідомлення бота прикріплено статичне PNG: вершини — гаманці (покупці й джерела), колір/групування — за кластерами, підписи — адреси-скорочення й частки. Інтерактивності немає: це ілюстрація до доказів, а не інструмент дослідження.

**Why this priority**: PRD вимагає картинку в повідомленні бота, а судді дивляться на неї в перші секунди; але рішення приймається за доказами, тож картинка — P2, а не ядро.

**Independent Test**: рендер збереженого результату кластеризації дає PNG, що відкривається переглядачем, має непорожній розмір і містить позначки кластерів (перевірка розбором пікселів/метаданих, не побайтова рівність).

**Acceptance Scenarios**:

1. **Given** результат із двома кластерами, **When** зрендерено PNG, **Then** файл відкривається, вершини двох кластерів візуально розрізнені, легенда називає частки.
2. **Given** результат без кластерів, **When** зрендерено PNG, **Then** картинка показує покупців без груп і підпис «кластерів не знайдено».

### User Story 4 - Кеш і час відповіді (Priority: P2)

Повторний запит того самого токена (API чи бот) повертає збережений результат миттєво, без повторного збору й перерахунку. Холодний запит живого токена вкладається в 60 секунд.

**Why this priority**: PRD вимагає відповідь до 60 секунд на холодному запиті й кеш; демо (повторний показ того самого токена) без кешу виглядає зламаним.

**Independent Test**: два послідовних запити того самого токена — другий не викликає збір (лічильник викликів транспорту не росте) і повертає побайтово той самий документ; холодний прогін записаного сценарію вкладається в бюджет.

**Acceptance Scenarios**:

1. **Given** токен уже проаналізовано, **When** надходить повторний запит, **Then** відповідь повертається з кешу без звернень до RPC і збігається з першою побайтово.
2. **Given** новий токен, **When** надходить перший запит, **Then** повний цикл збір→граф→кластери→відповідь завершується до 60 секунд (виміряно на сценарії типового розміру).

---

### Edge Cases

- `mint` не base58 / неіснуючий токен / токен без історії купівель → явна помилка, не стек і не зависання.
- Токен з 0 покупців у вибірці → «немає даних», а не «чисто».
- RPC-таймаут посеред збору → відповідь зі статусом неповноти й причинами (принцип V), кешується як неповна чи не кешується взагалі — фіксує план, не ця спека.
- Два одночасні запити одного нового токена → один збір, дві однакові відповіді (без подвоєння роботи й гонки).
- Докази, довші за ліміт повідомлення Telegram (~4096 символів) → стислий перелік у повідомленні + повний текст за кнопкою/файлом.
- PNG порожнього графа → підпис замість порожньої картинки.
- Перезапуск процесу → поведінка кешу документована (план фіксує: пам'ять чи диск).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-004-01**: Система MUST надавати `GET /api/token/{mint}`, що повертає `mint`, `analyzed_at`, `wallets_analyzed`, `clusters[]` (спадно за часткою; у кожному `wallets`, `supply_share`, `confidence`, `evidence[]` з типом, джерелом і вікном), `risk_score` 0–100 і смугу зі списком причин.
- **FR-004-02**: Запит MUST проганяти живий конвеєр 001→002→003 тими самими версіями конфігів і порогів, що й бібліотека; жодних окремих «демо-порогів» для API/бота.
- **FR-004-03**: Telegram-бот MUST відповідати на `/check <mint>` одним повідомленням: смуга й число ризику, частки найбільших кластерів, PNG-картинка, кнопка «докази».
- **FR-004-04**: Кнопка «докази» MUST показувати перелік доказів по кластерах, на яких побудовано число (тип, джерело, вікно); число без розкриття доказів MUST NOT вважатися показаним.
- **FR-004-05**: PNG MUST рендеритися на сервері зі результату аналізу (статичне зображення, без інтерактивності); кластери MUST бути візуально розрізнені з легендою часток.
- **FR-004-06**: Результат MUST кешуватися за адресою токена: повторний запит повертає збережений документ без повторного збору; холодний запит типового токена MUST завершуватися до 60 секунд.
- **FR-004-07**: Невалідний або неіснуючий `mint` MUST давати явну помилку (API — статус 4xx з поясненням; бот — зрозуміле повідомлення) без падіння процесу.
- **FR-004-08**: API і бот MUST працювати без авторизації (PRD: «жодної авторизації»).
- **FR-004-09**: Тести MUST працювати без мережі: живий RPC і Telegram — лише записані фікстури/несправжній транспорт (принцип II).
- **FR-004-10**: Секрети (токен бота, RPC-ключ) MUST надходити лише з оточення й MUST NOT потрапляти в репозиторій.
- **FR-004-11**: Жодна нова константа API/бота, що змінює кластери, впевненість, `risk_score` чи смугу, MUST NOT з'являтися поза версіонованими YAML 001/002/003; суто показові сталі (розкладка PNG, довжина підписів) документуються з фічею й на висновок не впливають.
- **FR-004-12**: Відповідь MUST нести походження висновку: версії конфігів 001/002/003, `analyzed_at`, статус повноти з причинами; смуга `insufficient_data` MUST NOT перетворюватися на «чисто» жодним шаром доставки (принцип V).

### Key Entities

- **Відповідь API**: документ з полями PRD-таблиці + походження (версії, повнота); кешується за `mint`.
- **Повідомлення бота**: текст (ризик, частки), прикріплене PNG, кнопка «докази» з розкриттям.
- **Картинка графа**: статичне PNG з результату кластеризації; легенда часток.
- **Запис кешу**: `mint` → документ відповіді + час створення; політика інвалідації — за планом.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: користувач надсилає боту `/check` з адресою інсайдерського токена зі збереженої дев'ятки й за ≤ 60 секунд отримує повідомлення зі смугою вище «чисто», частками кластерів, PNG і кнопкою доказів.
- **SC-002**: повторний запит того самого токена повертає побайтово той самий документ без нових звернень до RPC (лічильник транспорту не росте).
- **SC-003**: відповідь API для збереженого токена містить усі поля PRD-таблиці; кожен кластер має ≥ 1 доказ із джерелом і вікном; документ валідний проти зафіксованого контракту відповіді.
- **SC-004**: невалідний `mint` дає 4xx з поясненням (API) і зрозуміле повідомлення (бот); процес лишається живим; жодного стеку в користувацькій відповіді.
- **SC-005**: сценарний прогін (3 інсайдерські + 3 чисті зі збереженої дев'ятки через API/бот без мережі) показує кластери з доказами на інсайдерських і не вигадує їх на чистих — відповідно до критерію успіху PRD.

## Assumptions

- **Живий конвеєр**: кнопка й ендпоінт женуть той самий код 001→002→003, що й тести; RPC-доступ — через ключ в оточенні оператора демо (не в репо).
- **Бот відкритий усім** (без авторизації за PRD); захист від спаму — поза обсягом MVP.
- **Опитування vs вебхук**: бот працює довгим опитуванням в одному процесі із сервісом (найпростіше для демо); якщо розгортання вимагатиме вебхук — оформить план, семантика відповідей не зміниться.
- **Кеш у пам'яті процесу** без інвалідації за часом на вікно демо (токени не «псуться» за години); персистентність і TTL — рішення плану, поведінка при перезапуску документується.
- **Поза обсягом 004**: інші мережі, моніторинг, ML, авторизація/тарифи, бектест, сховище графа, складний UI, саме розгортання й подача (чекліст PRD — ручні кроки оператора, не вимоги цієї фічі).
- **PNG**: растровий статичний рендер; точний алгоритм розкладки — рішення плану, тест перевіряє зміст (кластери розрізнені, легенда є), а не побайтову рівність.
- **Частка пропозиції**: API називає поле `supply_share` за PRD, але обчислює його як частку серед проаналізованих покупців (assumption фічі 003 — загальної пропозиції в даних збору немає); контракт називає знаменник явно.
