# Known issues: публічний API і Telegram-бот доставки аналізу (004)

Відомі обмеження фічі на момент завершення (2026-10-05). Це не дефекти, що блокують мерж;
кожен пункт — свідоме рішення або відкладена робота.

**Ревʼю**: незалежний прохід Claude Opus — **CHANGES_REQUESTED** (5 пунктів), усі закрито
в цьому ж циклі: polling-бот більше не вмирає на таймаутах long-poll (таймаут клієнта 70 с
> 60 с вікна, `try`/backoff навколо `get_updates`, тест із транспортом, що кидає);
`evidence_preview_limit` йде з `delivery.yaml` через `run_polling` без умовчання в коді;
порожнє PNG несе ризик/смугу (`empty_caption`, тест без OCR); легенда переноситься,
переповнення вершин чесно рахується (`wallets_shown`/`wallets_total`, `+N` позначки),
палітра розширюється детерміновано (colorsys), фундери беруться з `source` доказів;
тести посилено (відмова×2 без кешування, імʼя змінної в stderr, конкретні очікування
по чистих, grep секретів на весь репозиторій). Мутаційні перевірки: remap смуги,
пропуск доказу, злам single-flight — червоні з очікуваної причини.

## 1. Живі шляхи покриті лише ручним димом

- `serve()` (сокети), нескінченний `run_polling`, справжній `HttpxBotTransport`,
  happy-path `main()` (блокується назавжди) — автоматизованих тестів немає за визначенням
  (мережа/сокети заборонені гардом); покрито лише `quickstart.md` §5 з ключами оператора.
  Fail-fast гілки (`--no-bot`, відсутні змінні з іменами в stderr) протестовані.
- Холодний живий запит жодного разу не виміряно (немає ключів): бюджет 60 с тримається на
  бюджеті збору 001 (40 с) + мілісекундах 002/003, але перший живий дим мусить зафіксувати час.

## 2. Памʼять процесу, без персистентності

- Кеш доставки й реєстр `request_id` (межа 1000, старі витісняються) — памʼять процесу:
  перезапуск чистить кеш, старі кнопки відповідають «запит застарів» (протестовано).
- Неповний результат кешується як неповний — свідомо (інакше повторний запит дав би інший
  `analyzed_at` і порушив SC-002); тимчасовий збій RPC «отруює» відповідь до перезапуску.
- Інвалідації немає; після хакатону потрібні TTL/персистентність — окрема задача,
  контракт відповіді не зміниться.

## 3. Межі навантаження демо

- Single-flight діє лише в межах одного `mint`: N різних токенів одночасно = N паралельних
  конвеєрів без глобального обмеження. Для демо достатньо; для ширшої публікації додати
  семафор — до відкриття URL ширше за суддів.
- HTTP слухає лише `127.0.0.1`: віддалене демо — через reverse proxy/SSH-тунель (ops).
- Бот відкритий усім без антиспаму (assumption spec): URL інстанса не світити ширше за подачу.

## 4. Формати

- Документ-помилка (`{mint, error:{kind, detail}}`, HTTP 4xx/5xx) — інша форма, ніж схема 004.1;
  споживач API мусить обробляти обидві. За потреби — друга схема `api-error-1.json`.
- Текст PNG — лише ASCII (покриття бітмап-шрифта Pillow); українська — лише в текстах
  повідомлень бота (рендерить клієнт). Кирилицю в картинку не додавати без перевірки гліфів.
- `Pillow` зафіксовано 12.3.0; тести використовують `get_flattened_data` (заміна
  депрекейтед `getdata`, видалення в Pillow 14).
- При `wallets_analyzed == 0` причини повноти — лише `["empty_input"]`: у цьому стані
  повнота збору тривіально повна, тож нічого не ховається.

## 5. Успадковане від ядра (на що чесно вкаже доставка)

- cln4 дає `risk_score 25` («підозріло») на чистім за міткою токені — хибне спрацювання 003,
  зафіксоване в `calibration.md` 003; бот покаже його як є, з доказами. Оператору демо —
  не обирати cln4 «чистим» прикладом.
- Усі живі відповіді зараз `insufficient_data` замість «чисто» (збори без делегованих
  купівель); якщо судді питатимуть «а що було б на повних даних» — відповідати звітом
  `evaluate`, не здогадками.

## 6. Дрібниця покриття

- Fast-path `if mint in self._docs` усередині `single_flight` прямо не тестується:
  його прибирання лишає набір зеленим (зовнішня перевірка `analyze()` перекриває).
  Мутація власне механізму single-flight червоніє 3/3. Прийнято свідомо.
