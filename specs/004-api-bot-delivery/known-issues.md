# Known Issues: 004 API + Bot Delivery

## 1. MELT price manipulation ≠ funding coordination (architecture)

**Суть:** MELT-мітки (`data/label/label.csv`) позначають токени, де була **маніпуляція ціною** (ризкий пулл, дамп, негативний `return_ratio`). Наш алгоритм детектує **фінансову координацію** — спільні фондери покупців, однакові суми, покупки в один слот.

**Чому це не баг:** інсайдери можуть купувати через різні фондери (ми не бачимо кластер), але ціну не дампувати (MELT = clean). І навпаки: токен може дампуватися (MELT = manipulated), але інсайдери могли фінансуватися з одного гаманця — тоді ми знайдемо кластер.

**Результат експерименту (4 токени, ground truth):**
- `8usLoMyo` (MELT high, prob=0.0) → risk=35, suspicious, кластер 97% (same_amounts, same_slot, shared_funder)
- `3imrYAzS` (MELT high, prob=0.0) → risk=4, clean (слабкий фінансовий сигнал)
- 2 MELT low токени → очікувано clean

**Дія:** Жодних змін коду. Документуємо як known limitation. Для користувача: `risk_score` + смуга — це оцінка *фінансової концентрації*, не *price manipulation*.

## 2. MLP модель MELT інвертована

Найкраща модель `mlp_pred_8` (AUPRC 0.574) навчилася передбачати «чисті» токени (`prob`≈1.0 = clean, `prob`≈0.0 = manipulated). Використання її скорів для ранжування інсайдерів дає **інвертований порядок**.

**Дія:** Не використовувати MLP-скори для ранжування. Ground truth беремо з `data/label/label.csv` (label=high/low).

## 3. Поріг `time_budget_seconds=600` для живої мережі

Збільшено з 40 на 600 с (ingest.yaml v3) для живого бота через Helius. На фікстурах (30 покупців, глубина 2, кап 30) збір займає 1–5 с; на реальних токенах з 1000+ покупцями — 60–300 с.

**Ризик:** Дуже великі токени (популярні пулли) можуть не вкладатися навіть у 600 с. `resume` працює коректно, але користувач чекає.

**Мітигація:** `resume` продовжує з того ж місця; повторний запит кешується.

## 4. `computed_band` = `null` для incomplete графів

У доставці 004 поле `computed_band` повертається `null`, якщо `graph_status != "complete"`. Це чесно (немає повного графа — негадаю), але клієнти можуть не очікувати `null`.

**Дія:** В контракті API (`api-response.schema.json`) поле позначене як optional.

## 5. PNG-картинка статична, без інтерактивності

Рендер через Pillow (T-093). Великі графи (100+ вершин) стають нечитабельними. Легенда показує частки, але мітки вершин скорочені до 6 символів.

**Дія:** Це P2 за PRD. Для демо — ок. Для продакшну — окремий фронтенд/візуалізація.

## 6. Кеш у пам'яті, без TTL і персистенції

`DeliveryCache` (T-091) trzymaє все в `dict`. Перезапуск процесу — повний холодний старт.

**Дія:** За планом 004 — персистентність і TTL поза MVP. Для демо (години) — ок.

## 7. Bot polling без вебхуків

Long-polling (`getUpdates` timeout=60) — просто, але не масштабується. Rate limits Bot API (30 req/s) можуть стати вузьким місцем при навантаженні.

**Дія:** MVP — polling. Вебхук — окрема задача якщо потрібно.

## 8. Немає авторизації / rate limiting

PRD: «жодної авторизації». Бот і API відкриті. Спам — захований через `DeliveryCache` (повторний запит = кеш) і `evidence_preview_limit=4000` у Telegram.

**Ризик:** Зловмисник може DoS-ити RPC (нові minти → збір). `time_budget_seconds=600` і `single_flight` обмежують шкоду одним токеном.

## 9. `hub_addresses.yaml` v1 — порожні exchange/MM списки

Списки `exchanges` і `market_makers` у `hub_addresses.yaml` порожні (v1). Хаби не відсікаються, крім системних програм і DEX.

**Дія:** Калібрування адрес — окрема задача (після збору даних про реальні exchange/MM гаманці).

## 10. Делеговані покупки (003) не аналізовані у фікстурах

Усі 9 фікстур `tests/fixtures/real/` зібрано з `delegated_analyzed: false`. Делеговані ребра (`delegated_buy` evidence) відсутні.

**Дія:** Включити при оновленні фікстур (фічя 005+).
