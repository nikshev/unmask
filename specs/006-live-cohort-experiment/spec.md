# Feature Specification: Живий когортний експеримент 30+30

**Feature Branch**: `006-live-cohort-experiment`

**Created**: 2026-10-07

**Status**: Draft (blocked on owner inputs — see §Inputs)

**Input**: Owner decisions (2026-10-07, fixed — do not reopen):
1. Cohort A = screen a candidate pool through pipeline 001→002→003, take TOP-30 by `risk_score`.
2. Cohort B (control) = 30 liquid tokens (SOL, USDC, BONK, JUP, WIF, POPCAT, … — same universe as the 005 clean set).
3. The live run is executed by the agent from here once inputs arrive.
4. Results land in README (new section replacing/extending the 4-token MELT section) and extend the 005 ground truth where valid.

## Background

The 40-token MELT run (README, 2026-10-07) was methodologically void: the MLP
model is inverted (its top scores = cleanest tokens), and the "random" sample came
from the prediction CSV, not ground truth. The 4-token ground-truth check shows the
right direction (financial clusters ≠ price manipulation) but is not statistical.
This feature is the representative experiment the README caveats demand.

## User Scenarios & Testing

### User Story 1 — Cohort lists (Priority: P1)

**Description**: Two versioned mint lists: `cohort_a_pool` (screening pool, ≥100
MELH-high ground-truth mints) and `cohort_b` (30 liquid-token mints). Format —
JSONL v1 per `contracts/cohort.schema.json`.

**Independent Test**: schema validation of both files; pool ≥ 100 mints, control
exactly 30; all mints valid base58.

**Acceptance Scenarios**:
1. **Given** the owner provides a MELT-high mint list, **When** it is converted to
   `cohort_a_pool.jsonl`, **Then** schema validation passes and the mint count ≥ 100.
2. **Given** the fixed liquid universe, **When** `cohort_b.jsonl` is built, **Then**
   it holds exactly 30 mints, disjoint from the pool.

### User Story 2 — Live screening + selection (Priority: P1, manual)

**Description**: Run the 005 runner in `--live` mode over the pool with the frozen
fixture profile (first 30 buyers, depth 2, cap 30, no SPL; ingest v3 / hubs v3 /
clusters v2), rank by `risk_score` (tie-breaks: more clusters, then larger max
share), take top 30 → `cohort_a.jsonl`. Then run the same profile over cohort B.

**Independent Test**: rerun determinism on recorded outputs (same ranked list from
the same per-token docs); no pytest touches the network — the live steps are
manual gate tasks, not tests.

**Acceptance Scenarios**:
1. **Given** RPC key + pool file, **When** screening finishes, **Then**
   `cohort_a.jsonl` holds exactly 30 mints with rank, score, band, latency stats.
2. **Given** the same profile, **When** cohort B is analyzed, **Then** all 30 docs
   validate against schema 004.1.

### User Story 3 — Comparison + publication (Priority: P2)

**Description**: Descriptive comparison A vs B (risk_score median/p25/p75, share of
tokens with ≥1 cluster, evidence-type histogram, band split) with preregistered
expectations; a new README section; optional 005 ground-truth extension for
tokens with confirmed coordination.

**Independent Test**: analysis script runs offline on committed summary files and
regenerates the published numbers byte-identically.

**Acceptance Scenarios**:
1. **Given** committed summaries, **When** the analysis runs, **Then** the README
   numbers match the script output exactly (no hand-copied statistics).

## Requirements

### Functional Requirements

- **FR-006-01**: Cohort lists MUST be versioned JSONL (`version: 1`) with fields
  `mint`, `cohort` (pool_a|a|b), `source` (melt_high|liquid|screen_rank), `notes`;
  schema `contracts/cohort.schema.json` (draft 2020-12).
- **FR-006-02**: Screening MUST use the frozen fixture profile (N=30, depth=2,
  cap 30, no SPL) and record config versions per token (ingest v3, hubs v3,
  clusters v2).
- **FR-006-03**: Selection MUST be top-30 by `risk_score` desc, tie-breaks:
  `clusters_count` desc, then `max_share` desc, then mint asc (deterministic).
- **FR-006-04**: Control cohort MUST be exactly the 30 committed liquid mints;
  substitution requires a new list version + CHANGELOG-style note in the spec dir.
- **FR-006-05**: Committed artifacts per token MUST be limited to: mint, rank,
  risk_score, band, clusters_count, max_share, coordination_category, latency,
  rpc_calls. Raw per-token JSON and secrets MUST NOT be committed.
- **FR-006-06**: Comparison MUST report preregistered expectations vs outcome
  (median risk A > B; share-with-cluster A vs B; evidence histogram) without
  accuracy overclaims (exploratory, n=30+30).
- **FR-006-07**: README MUST gain a section with the cohort table + caveats,
  numbers generated by the analysis script, never hand-copied.
- **FR-006-08**: Live steps MUST be manual gate tasks (`--live` runner), never
  pytest; offline steps MUST run without keys or network.

### Non-Functional Requirements

- **NFR-006-01**: Screening one token MUST respect `time_budget_seconds=600`;
  pool of 120 ≈ 2–10 h wall (60–300 s/token observed); full 30+30 ≈ +1–5 h.
- **NFR-006-02**: Every live token MUST log RPC calls + latency; a run manifest
  records command, config digests, start/end times.

## Key Entities

- **CohortList**: versioned mint list with cohort label + source (committed).
- **ScreeningRun**: per-token live docs + manifest (raw docs NOT committed).
- **CohortSummary**: committed per-token summary row (FR-006-05 fields).
- **Comparison**: offline analysis output feeding README numbers.
