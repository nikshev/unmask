# Відомі обмеження фічі 001 (на 2026-10-04)

Записано за результатами ревʼю T-009…T-018. Жодне не порушує FR, жодне не дає хибного «чисто»: усі дають чесний `incomplete` або явне обмеження. Рішення про усунення — за власником, до початку фіч, що залежать від повноти даних.

## 1. ~~Resume не прогресує для «важкого» гаманця при малому бюджеті~~ — ЗАКРИТО T-022 (2026-10-04)

Додано мемо завершених сканувань джерел (`CollectionState.scan_memo`): кожен повторний прохід гарантовано просувається щонайменше на одне завершене сканування (історія гаманця/токен-рахунку або список токен-рахунків). Виміряно на basic при 1 с/виклик: бюджет 3 с — раніше «ніколи», тепер 30 повторів; 6 с — 11; 10 с — 6 (було 8).

**Залишкова межа**: бюджет, менший за суму (звернення, що повторюються на кожному проході — крок 4 сервісу, пошкоджені транзакції — і найдорожчого одного сканування джерела), назавжди дає чесний `incomplete`. Задокументовано в `funding.py` і закріплено тестом `test_budget_shorter_than_any_source_scan_honestly_never_completes`. Нотатки ревʼю: мемо на свіжому прогоні тримає записи всіх вершин рівня до кінця рівня (лінійно, але більше за «лише обірвані»); тест не ловить мутацію «на мемо-хіті токен-рахунку відкинути найновіший запис» (ловить fuzz) — варто додати кейс, коли запис токен-рахунку не досяжний через історію гаманця.

## 2. Правило купівлі R-2 (T-010, ревʼю)

- **swap-and-send** (Jupiter з `destinationTokenAccount` іншого власника; бот купує на свіжий гаманець): платник не отримує токен, отримувач нічого не віддає — покупки не бачить ніхто. Це важливий патерн для пошуку інсайдерів.
- Рента створених рахунків приписується fee payer незалежно від того, хто її фінансував → можливі хибні покупці/пропущені покупці на краях.
- Пули/криві при продажу користувача потрапляють у покупці з `address_type=off_curve` і займають місця серед перших N до відсікання хабів (фіча 002).

## 3. Токени token-2022 з transfer-fee (T-008/T-009)

`transferCheckedWithFee` не розбирається; кожен такий переказ → `CorruptRecord` → `unresolved_transfer`; результат для таких mint завжди `incomplete` (чесно, але марно). Потрібна окрема підтримка (брутто/нетто суми).

## 4. Продуктивність на токенах зі 100k+ транзакцій (R-7)

Перегортання історії mint послідовне (≥100 викликів при page_size=1000); 40 с не гарантується; результат — чесний `incomplete` з курсором. Паралелізм (`rpc.max_concurrency`) у ядрі не використовується.

## 5. Дрібні

- `_token_account_entries` викликається на кожній сторінці (≈0,5 с на 80k записів).
- Підпис ребра відсутній в історії відправника (делегат): `before=` на живому RPC працює за слотом; у `FixtureRpcSource` — `ValueError`. Перевірити в `HttpRpcSource` (T-021).
- `Asset(str)` без `__slots__` (безпечно, але розрив у «повній» незмінності).
- Тести фічі повільні (≈40 с, з них матриця збоїв ≈27 с) — за потреби позначити `slow`.
- `fuzz14_strict` на 1500 ітерацій падає на припущенні харнеса (перестановка записів одного слота між проходами); живий RPC такого не робить.

## 6. Знахідки першого живого прогону (2026-10-04) — T-049, T-050

Перший запуск проти реального Solana RPC (RPC Fast, ключ користувача) показав те, чого не бачили фікстури:

1. **Версія транзакцій 1** (≈25–35% свіжих транзакцій): `maxSupportedTransactionVersion: 0` → помилка `-32015` → пачка «все або нічого» ламається → збір `incomplete`. Лікує T-049 (`max_tx_version=1`).
2. **Ліміт провайдера — ШВИДКІСТЬ, а не розмір batch**: кошик токенів на кількість `getTransaction`-елементів (виміряно: ємність ≈ 40, поповнення ≈ 15–16/с; нестача → HTTP 429/`-32005` без `Retry-After`); ядро шле пачки по `rpc.page_size`=1000. Лікує T-049: під-batch `max_batch=25` + клієнтський пейсер `tx_rate_per_second=12`, `tx_burst=30` (дефолти з запасом ≈ 20–25%; 20/40 давали 429 у кожному живому прогоні). Перевірено на живому вузлі: 150 підписів — 10,1 с, 8×25 — 12,7 с, 0 відповідей 429. **Наслідок для продукту**: пропускна здатність ≈ 30 + 12·40 ≈ **510 транзакцій на холодний запит** (бюджет 40 с); токен із перевищенням — `budget_exhausted`/`incomplete` і продовження через resume (T-022). Це залежить від тарифу RPC Fast: потрібен вищий тариф або архівний endpoint з вищим лімітом для демо на великих токенах.
3. **Ефемерні токен-рахунки** (≈36% транзакцій корпусу: Jupiter-свопи з тимчасовим WSOL): немає в pre/post токен-балансах → `CorruptRecord` → `incomplete`. Лікує T-050 (власник з `initializeAccount*` у тій самій транзакції).
4. **Глибина історії вузла ≈ 21,5 год** (`getFirstAvailableBlock` = слот 452998338 ≈ 2026-10-03 17:17 UTC): токени старші за ~добу недосяжні через цей ключ (перелічення перших N покупців потребує всієї історії mint). Потрібен архівний endpoint для історичних (демо-)токенів. **Не виправляється кодом.**
5. Високонавантажені адреси (wSOL mint, програма pump.fun): `getSignaturesForAddress` → `-32005` (ліміт). Це очікувано для хабів (див. фічу 002).
6. **Перший збір на реальному токені (`95DELX…pump`, 5880 транзакцій) дав нульовий прогрес** (2026-10-04): `rpc.page_size`=1000 керував і сторінкою підписів, і розміром batch транзакцій; виклик на 1000 транзакцій при пейсері 12/с триває 80+ с > бюджету 40 с, «все або нічого» викидає 475 уже отриманих → `buyers=0`, resume не допомагає. Лікує T-052 (`rpc.tx_batch_size=25`, конфіг v2). Також T-051: бюджетний `RpcTimeout("budget")` пейсера класифікувався як `timeout`, а не `budget_exhausted` — виправлено T-051 (`RpcBudgetTimeout`, підклас `RpcTimeout`).

## 7. Огляд публічних/спільнотних Solana RPC (2026-10-04; виміряно)

Перевірено безкоштовні endpoint-и без ключа тими самими вимірами, що й ключ користувача (`getFirstAvailableBlock`, давня транзакція лютого 2025, `getSignaturesForAddress` для токена лютого 2025, batch `getTransaction`):

| Вузол | Глибина історії | Пропускна здатність | Висновок |
|---|---|---|---|
| ключ користувача (RPC Fast, free «Start», 15 RPS) | **~21,5 год** | ≈15–16 tx/с (лічать кожен елемент batch) | недостатньо для історичних токенів |
| `solana-rpc.publicnode.com` | ~1 доба (заява «archive» не підтверджена) | не міряли | не архівний |
| `rpc.solanatracker.io/public` | ~1 доба | не міряли | не архівний |
| `api.mainnet-beta.solana.com` (Solana Foundation) | **архівний** (`getFirstAvailableBlock=0`; знайшов лют. 2025, віддав історію токена) | free: `x-ratelimit-method-limit: 10` ≈ **1 getTransaction/с**, 429 на більшості | придатний лише для разових експериментів над малими токенами |
| `public.rpc.solanavibestation.com` | архівний (від слота ~297M), давня транзакція знайдена | `getSignaturesForAddress` ок, batch → 429 | потрібен ключ |
| `solana-mainnet.gateway.tatum.io` | `getFirstAvailableBlock=0`, давня транзакція знайдена | `getSignaturesForAddress` → помилка `-16401` (недоступний на free) | без підписів не працює |
| OnFinality, Pocket, dRPC, 1rpc, Blockdaemon | — | 429 / 403 / 400 / недоступні без ключа | непридатні без ключа |

Висновки: безкоштовного й водночас швидкого й архівного вузла без ключа немає. Реальні шляхи: (1) вищий тариф/кредити RPC Fast (спонсор треку; «Stream» ≈ 150 RPS, ×10); (2) ключі безкоштовних тарифів з архівом — Alchemy (заявлено 25 RPS, повна історія), Helius (10 RPS; `getTransactionsForAddress` — до 100 повних транзакцій за один виклик — лише на платних планах, що знімає обмеження «запитів на елемент»); (3) метод, дешевший за транзакціями (див. T-053: SPL off, менший кап підписів, пропуск «активних ботів»).
