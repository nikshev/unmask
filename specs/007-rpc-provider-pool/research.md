# Research: Пул RPC-провайдерів (007)

Вхідні факти: `HttpRpcSource` — однопотоковий, глобальний кошик одиниць на всі методи, «все або нічого» на
виклик `get_transactions`, власні повтори; ядро викликає джерело послідовно, `get_transactions` пачками
`rpc.tx_batch_size = 25`, `None` від `get_transactions` ядро вже мапить у `unavailable`; RPC Fast Start —
глибина ≈ 21,5 год, `getTokenAccountsByOwner` заблоковано; Helius free — архівний, ≈ 4,5 од/с, кошик 20.

## R-1 Де живе паралелізм

**Рішення**: всередині `PooledRpcSource.get_transactions` (реалізує `RpcSource`); колектор не змінюється.
Раунд = набір часток (≤ 1 на провайдера), виконаних через `runner`; обробка результатів — у головному потоці.

**Чому**: колектор послідовний і детермінований; паралелізм на рівні пачки не торкається порядку звернень
ядра (`rpc_calls` і журнали ядра ті самі). Кожен провайдер у раунді отримує рівно одну задачу, тож адаптер
ніколи не використовується двома потоками одночасно в межах виклику; лок на провайдера закриває випадок
кількох одночасних аналізів (008). `Deadline` лише читається потоками (`SystemClock` безпечний).

**Відкинуто**: (а) паралелізм у колекторі — зміна логіки 001, ризик для resume; (б) потоки всередині
`HttpRpcSource` — ламає модель кошика й однопотоковість адаптера; (в) asyncio — переписування транспорту.

## R-2 Звідки пул знає вік

**Рішення**: кеш `signature → blockTime` із відповідей `getSignaturesForAddress`, що пройшли через пул.
Ядро завжди спершу перегортає історію (mint або гаманця), потім тягне транзакції цих підписів — тож вік
відомий майже завжди. Невідомий вік (`blockTime: null`, витіснення з кешу) → придатні всі, але `None` від
неархівного не остаточне (FR-007-07). Кеш обмежений `age_cache_entries` (FIFO): він лише оптимізує
маршрут, на результат не впливає — правило підтвердження гарантує правильність і без нього.

**Відкинуто**: `getBlockTime`/`getFirstAvailableBlock` на кожен запит — зайві одиниці лімітера.

## R-3 Розподіл за пропускною здатністю

**Рішення**: метод найбільших залишків за вагами `rate_per_second` профілю придатних провайдерів; нічия
залишків — порядок конфігу; частки — суцільні відрізки позицій у порядку конфігу. Позиції «лише архівні»
(відомо старі) діляться окремо між архівними, решта — між усіма придатними. `max_batch` кожен адаптер
застосовує сам до своєї частки (edge case spec). Одиночні виклики — SWRR за тими самими вагами.

**Чому**: детерміновано, просто, без стану кошика; профіль уже відображає виміряну швидкість.
Динамічне перерозподілення за вимірюванням — поза обсягом (spec Assumptions).

## R-4 Відмови, пауза, клас помилки

**Рішення**: частка, що впала з `RpcError`, у наступному раунді ділиться між іншими придатними (провайдер
виключається до кінця виклику). `RpcRateLimited` → пауза провайдера `max(rate_limit_cooldown_seconds,
retry_after or 0)` за `clock.monotonic()` пулу; на паузі провайдер не отримує нових часток/запитів, якщо є
інші; якщо на паузі всі — пауза ігнорується (політика не може сама валити збір). Немає кому віддати →
піднімається **той самий об'єкт винятку** останньої спроби для найменшої нерозв'язаної позиції (клас
і фіксований текст адаптера, FR-007-08), поза блоком `except` (без `__context__`, як в адаптері).
`RpcBudgetTimeout` частки чи одиночного виклику — стан кошика конкретного ключа, тож перебирається як
інші (інший провайдер може мати повний кошик), без паузи; перед кожним раундом/спробою `deadline.expired()` →
свіжий `RpcBudgetTimeout` без звернень. Позиція без власної помилки (чекала підтвердження `None`), для якої
не лишилось придатних, отримує помилку останнього виключеного придатного для неї провайдера; лише якщо такого
немає — `RpcUnavailable("history beyond provider retention")`. Будь-який не-`RpcError` — дефект: піднімається
одразу після раунду (не маскується).

## R-5 `getSignaturesForAddress` і неархівні

Коротка сторінка неархівного вузла означає «у моєму сховищі більше нічого», а не «в адреси більше нічого» —
незалежно від віку курсора (старіші записи можуть бути за межею). Тому: підписи — лише архівним, поки є
придатний архівний; неархівний — запасний, і тоді приймається лише повна сторінка (`len == limit`);
коротка/порожня → `RpcUnavailable("history beyond provider retention")`. На практиці (`page_size = 1000`)
підписи йдуть на Helius, а RPC Fast обслуговує `getTransaction` свіжих транзакцій і `getAccountInfo` —
тобто працює в основному трафіку (US2-4).

## R-6 Конфіг, фабрика, зворотна сумісність

Формат і перевірки — як `delivery.yaml` (усі ключі обов'язкові, невідомі — `ConfigError` з назвою поля);
журнал перевіряє тест через `hubs.config.check_changelog` (`ingest` не імпортує `hubs`). Відсутній файл →
пул з одного провайдера `UNMASK_RPC_URL`, `archival: true`, профіль — аргумент (`rpcfast_start` у сервісі,
`helius_free` у воркері, як зараз) — одна кодова гілка, потокобезпечність і для старого режиму.
Невстановлена змінна → пропуск із попередженням (лише ім'я); встановлена, але невалідна → `ConfigError`
(лише ім'я): помилка оператора має бути гучною.

## R-7 Детерміновані тести паралелізму

- `runner`-шов: `SequentialRunner(order)` виконує задачі раунду в заданому порядку (прямий, зворотний,
  перестановки) → SC-003 без потоків.
- Справжня одночасність: `ScriptedProvider(barrier=threading.Barrier(n, timeout=5))` — послідовний пул
  зламав би бар'єр; на зеленому шляху час не вимірюється.
- SC-001: «віртуальна затримка» — кожен дубль журналює розмір частки; makespan виклику = max частки × d,
  послідовний = сума × d; перевірка ≤ 0,5. Справжній годинник — лише `-m perf`.
- Неархівність: дубль приховує записи з `blockTime < horizon` (транзакції → `None`, сторінки обрізаються).

## R-8 Лічильники

`ProviderStats(requests, units, failures_by_class, not_found_escalations, cooldowns)` за іменем із конфігу.
`stats()` — знімок; `stats_line()` — один рядок без URL; пишеться в лог на `close()`, воркер друкує після
кожного токена. Канал для сервісу (напр. `/healthz`) — справа 008.
