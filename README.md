# Unmask — insider cluster detection for Solana token launches

Takes a token address and returns clusters of related wallets with evidence.
Submission for Crypto World's Fair (Colosseum + Superteam Earn): Superteam Ukraine,
RPC Fast Infrastructure tracks, and — time-wise — Solami and Panta API. Deadline:
October 13, 06:59 UTC.

## How it works

Pipeline: `001 on-chain data ingest` → `002 funding graph without hubs` → `003 clusters
with evidence and 0–100 risk assessment` → `004 public API and Telegram bot`. No number
without evidence: every cluster carries a list of primary references (signatures, slots,
source addresses); incomplete data is never shown as "clean".

## Deploy

Runbook for one server behind nginx. No secrets are in this repository: keys and
tokens live only in the operator's `.env` file (mode 600, never committed).

Requirements: Linux with systemd, uv (Python package manager), nginx, certbot,
and a domain whose DNS record points at the server. `<DOMAIN>` below is a placeholder.

### 1. Install dependencies

```bash
cd /opt/unmask
uv sync --frozen --no-dev
```

### 2. Create `.env` (operator-owned)

```bash
cd /opt/unmask
touch .env && chmod 600 .env
```

Fill in the names below with your values (the names alone are shown here):

```text
UNMASK_RPC_URL=
UNMASK_RPC_URL_ALT=
UNMASK_BOT_TOKEN=
```

Write values without quotes, without spaces, and without `&`, `$` or `\` where
possible. systemd (`EnvironmentFile=`) and bash (`set -a; . ./.env`) read this file
differently: quotes, `&`, spaces, `$` and `\` can be interpreted by one and not the
other. A URL with `&` in its query string is the usual cause of a surprise: bash
treats an unquoted `&` as a background operator. Prefer a URL without `&`.

### 3. Run by hand first

```bash
cd /opt/unmask
set -a; . ./.env; set +a
uv run python scripts/serve_unmask.py --host 127.0.0.1 --port 18080
```

In a second shell: `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/healthz`
must print `200`.
Stop with Ctrl+C once it works.

### 4. Run as a systemd service

`deploy/unmask.service` restarts the process after any failure (`Restart=always`,
`RestartSec=5`) and reads the variables from `/opt/unmask/.env` through
`EnvironmentFile=`. The unit file itself contains no values. The unit runs as root
(it has no `User=`); see the comments in the file.

```bash
sudo cp /opt/unmask/deploy/unmask.service /etc/systemd/system/unmask.service
sudo systemctl daemon-reload
sudo systemctl enable --now unmask
systemctl status unmask --no-pager
journalctl -u unmask -n 100 --no-pager
```

After editing `.env`, run `sudo systemctl restart unmask`.

### 5. Reverse proxy with TLS (nginx)

`deploy/nginx-unmask.conf.example` is a template. Replace `example.com` with `<DOMAIN>`
and the certificate paths with the ones certbot creates. Obtain the certificate
before nginx loads the config, because the `ssl_certificate` files must exist. The hooks
stop nginx while certbot binds port 80 for the challenge and start it again afterwards:

```bash
sudo certbot certonly --standalone \
  --pre-hook "systemctl stop nginx" --post-hook "systemctl start nginx" \
  -d <DOMAIN>
sudo cp /opt/unmask/deploy/nginx-unmask.conf.example /etc/nginx/sites-available/unmask
sudo ln -s /etc/nginx/sites-available/unmask /etc/nginx/sites-enabled/unmask
sudo nginx -t && sudo systemctl reload nginx
curl -s -o /dev/null -w '%{http_code}\n' https://<DOMAIN>/healthz   # prints 200
```

The example redirects port 80 to HTTPS and proxies to `127.0.0.1:18080`. It overwrites
`X-Forwarded-For` with the connection address. The application trusts that header only
from the addresses in `proxy.trusted` (`127.0.0.1`, `::1`, see `config/protection.yaml`),
so nginx must run on the same host as the service. `proxy_read_timeout 1830s` is above the
1800 s analysis budget; a shorter timeout would turn cold analyses into 504 responses.
The example uses `listen 443 ssl http2;`, which works on nginx 1.24 and later.

### 6. Smoke check

```bash
deploy/smoke.sh <DOMAIN>                            # on the server: systemd Restart=always,
                                                    # HTTP -> 301, HTTPS /healthz 200,
                                                    # invalid mint -> 400
deploy/smoke.sh --local                             # http://127.0.0.1:18080: /healthz 200,
                                                    # invalid mint -> 400
deploy/smoke.sh --local http://127.0.0.1:18080 35   # also sends 35 requests to show a 429
```

The burst count must be larger than `api.requests_per_window` (30). The invalid-mint
request of the same run counts toward the same per-IP limit, so `1 + BURST` requests
inside one window exceed 30 and at least one of them gets 429. With `BURST` = 5 there
would be at most 6 requests, no 429, and the script would report FAIL.

The script exits 0 when every check passes, 1 when a check fails, and 2 on bad
arguments. It sends no keys and never sends a real token address: the mint it uses is
invalid and is rejected before any RPC call. The burst mode counts against the calling
IP's own limit, so your IP may get 429 for up to `api.window_seconds` afterwards.

### Limits

Limits live in `config/protection.yaml`. The file is versioned: the current version and
its sha256 are recorded in `config/CHANGELOG.md`. Any change means bumping `version`
and adding a changelog entry with the new sha256. Values in v1:

| Setting | Value | Meaning |
|---|---|---|
| `api.requests_per_window` | 30 | requests to `GET /api/token/{mint}` per client IP per window |
| `api.window_seconds` | 60 | length of the sliding window, in seconds |
| `heavy.max_concurrent` | 3 | cold (uncached) analyses running at the same time |
| `heavy.busy_retry_after_seconds` | 60 | `Retry-After` value sent when all analysis slots are busy |
| `bot.checks_per_window` | 5 | new tokens a Telegram user may check per window |
| `bot.window_seconds` | 600 | length of the bot window, in seconds |

Responses when a limit is hit:

- `429 Too Many Requests`, error kind `rate_limited`, with a `Retry-After` header:
  the client sent more requests than the per-IP limit allows.
- `503 Service Unavailable`, error kind `busy`, with a `Retry-After` header: all
  heavy-analysis slots are taken and the mint is neither cached nor already being analysed.
  Cached results and joining an analysis already running for the same mint are not
  rejected.

A 429 or 503 never means "clean" or "no data". It is an overload answer only, and the
body of a successful response is unchanged.

### RPC provider pool

The service uses the pool defined in `config/rpc_pool.yaml`. Only variable names are
in that file; the values go in `.env`:

- `UNMASK_RPC_URL`: RPC Fast Start. Not archival: about 21.5 hours of history.
- `UNMASK_RPC_URL_ALT`, `UNMASK_RPC_URL_ALT1`, `UNMASK_RPC_URL_ALT2`: Helius free
  keys. Archival.

A provider whose variable is unset is skipped with a warning. Setting only
`UNMASK_RPC_URL` is not enough: RPC Fast does not serve `getTokenAccountsByOwner` on
the Start tier, so the service exits with code 2. Set at least one `UNMASK_RPC_URL_ALT*`.

### Known limitations

- Limit state (request windows and busy slots) is kept in the memory of the service
  process. A restart (`systemctl restart`, a crash, or a reboot) resets all counters, so
  a client can start a fresh window right after a restart.
- The unit starts the service with `--host 127.0.0.1`, so port 18080 listens on the
  loopback interface only and nginx on the same machine is the only entry point. Without
  `--host` the service listens on all interfaces (`0.0.0.0`, the default): when you run it
  by hand, pass `--host 127.0.0.1` or block the port from outside, for example
  `sudo ufw deny 18080`.
- The per-client limit keys on the exact client address. Do not enable an IPv6 listener in
  nginx (`listen [::]:443`) until the limiter groups IPv6 clients by /64: a single /64 owner
  would otherwise get a separate window per address. A client can also hold all heavy-analysis
  slots with cold requests for up to the time budget; the per-client limit does not prevent that.

## 40-token MELT test (2026-10-07) — methodological caveats

A one-off live run of the 001→002→003 pipeline (not a test; fixtures and tests
untouched). List source — the public [MELT](https://github.com/git-disl/MELT)
dataset (41,470 pump.fun launches, December 2024 – March 2025): labels from
`data/label/label.csv` (ground truth), scores — model `results/mlp_pred_8_0.573976.csv`
(AUPRC 0.574) out of 6,491 scored tokens.

**Key methodological finding**: the MLP model is **inverted** — it learned to predict
"clean" tokens (label=low), not insiders. Its `prob`≈1.0 means "the model is confident
the token is clean", and `prob`≈0.0 means "the model is confident it is manipulated".
Therefore:
- "top-30 by MLP score descending" from the original experiment are actually the tokens
  the model considers the **cleanest** (false negatives for insiders).
- The "10 random MELT-low" sample was also drawn from the prediction CSV, not from
  ground truth — it contains tokens MELT labels `high` (manipulated) that the model
  mistakenly scored `label=0`.

A fair comparison must use **ground truth** (`data/label/label.csv`):
- MELT `high` (manipulated) — 34,890 tokens
- MELT `low` (clean) — 1,878 tokens

Ingest profile = the `tests/fixtures/real` fixture profile (first 30 buyers,
depth 2, cap 30, no SPL, Helius): configs ingest.yaml v3, hubs.yaml v3,
clusters.yaml v1. Raw JSON was not committed to the repository.

### 4-token ground truth check (2026-10-07)

| mint | MELT ground truth | MLP prob | risk_score | band | cluster (share, types) |
|---|---|---|---|---|---|
| 8usLoMyo… | high (manipulated) | 0.0000 | 35 | suspicious | 0.97, {same_amounts, same_slot, shared_funder} |
| 3imrYAzS… | high (manipulated) | 0.0000 | 4 | clean | — |
| 2FBQe11U… | low (clean) | 0.6691 | (pending) | — | — |
| 8i8g2YXw… | low (clean) | 0.8965 | (pending) | — | — |

**Conclusion**: our algorithm detects **financial clusters** (shared funders,
identical amounts/slots, direct transfers); MELT detects **price manipulation**
(return_ratio). These are **different signals** — full correlation is not expected.
A token can have a clean price (no dump) but insiders with shared funders — our
algorithm will find them. Conversely, a token can dump while its insiders were funded
through different paths — then we find no cluster.

Caveats: a 4-token sample is not statistical; no accuracy claims can be made.
A full experiment on a representative sample needs a separate spec/task.
